# 管理员自定义收款

任务 COLLECTION-20261009；类型 Feature；优先级 P1；基线 e2c2aeac0。

## 要求与验收

- AC1：仅有效管理员会话且完成二次验证可创建收款；拒绝 API key、普通用户和客户端指定受益账户。
- AC2：金额以整数分入参，范围 1–100000000 分（人民币 0.01–1000000 元），支持支付宝和微信，仍受中央通道限制；不修改普通充值目录及开关。
- AC3：持久类型 `collection`，`amount=0`、`pay_amount=实收金额`。可信付款只完成收款记录，不发余额、订阅、重置卡、并发或返佣。
- AC4：相同幂等键和参数重用订单；改变金额/方式冲突。未知创建结果保留同一订单重试；重复回调无重复权益。
- AC5：管理订单页可输入金额、选择渠道、生成/下载真实通道二维码、查看金额/有效期并刷新到账状态。通道只返回网页收银台时展示明确链接，不冒充原生二维码。
- AC6：保留取消、过期、晚到付款安全边界；收款订单暂不支持常规站内退款/开票，明确拒绝，不走余额扣回。取消后晚到款仍遵循既有原路退回安全规则。

## 架构决定与影响

复用既有 owner-test 的持久请求快照、稳定订单号、派发租约及 pay-v1 接口，新增私有收款模式和独立管理员入口。原 1–2 分测试约束保持不变，客户下单入口继续拒绝 collection。既有 order_type 为 varchar(20)，无需 DDL 或新表。独立订单类型让旧代码 fail-closed，不能将余额订单加一个隐式标记绕过充值。

上游支付基线 bdb42e22f81fcb633ff0a060961211dd2bcb515b 的 payment_order.go/payment_fulfillment.go 已核对；统一支付契约沿用 docs/UNIFIED_PAYMENT_INTEGRATION.md 固定源码，order_type 是产品所有的标识，中央服务不发产品权益。LGPL-3.0 义务不变。

## 执行 DAG

1. Root：架构/授权边界及契约检查 → 后端测试先失败 → 创建/回调/边界实现。
2. UI worker：依赖 1 冻结的 POST /admin/payment/collection/orders 契约，再实现订单页交互、API/类型/中英文本及组件测试；与后端不同时写同一工作区。
3. Root：整合、范围测试、类型/构建、可视检查；失败回到责任实现者。
4. 独立 QA/Review：冻结同一 diff，检查 AC1–6、持久化和并发安全；Root 修正后重验。

风险：实盘商户可能无 QR 接口权限，代码测试不能替代实际通道权限；不能通过绕过风控解决。旧二进制不认识 collection，回滚前应排空相关待支付/回调工作，保留财务记录，不删订单。2026-10-09 用户后续已授权发布；实际资金支付仍由用户操作。
