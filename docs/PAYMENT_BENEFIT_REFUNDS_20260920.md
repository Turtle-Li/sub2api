# 自动退款权益回收 — 2026-09-20

状态：开发中；关联清单 PAYMENT-FIX-20260920 / P19。基线 a025553c4。用户已明确授权开发、测试与发布，并取消 Sub2 支付宝和微信的每日退款总额限制。

## 产品规则

- 实际履约时记录订单的赠送重置卡批次 ID、数量、有效期，以及并发发放前/后数值和订单目标。不能仅记录当前套餐配置。
- 仅检查本订单实际发放的赠送重置卡；人工赠卡、其他订单购买的卡和其他套餐的赠卡不混入回收。
- 本订单赠卡有使用记录时，系统拒绝自动退款并说明原因；未使用的赠卡随退款预占、确认回收或失败释放。不得删除使用事实或把回收伪装成使用。
- 并发回收保留之后的其他订单、管理员操作和兑换权益。不能直接把用户当前并发覆盖成早先值，也不能把已有付费并发复制成永久免费权益。
- 任意一次成功退款（含部分退款）结束该订单的附加权益；钱和订阅期限仍按既有服务端剩余余额/时长规则核算。确认页先展示回收的卡和并发变化。
- 继续保留已开票禁止新退款、驳回允许、每订单最多一次成功退款、已付金额上限、币种校验和支付渠道自身约束。不限每日总额不等于放开单笔财务边界。

## 持久化和事务边界

当前实现新增 `payment_refund_benefit_sources`、赠卡来源关联与用户并发事件账本（精确表名以migration255为准），生命周期与现有退款attempt绑定。

沿既有 payment_wallet_fundings、payment_subscription_grants、unified_payment_refund_attempts，以及月度 schedule/issuance 账本扩展。不另建第二套资金状态机。

新来源账本保存实际权益事实；每个 PAYMENT_MAX 事件只关联订单权益状态，不能另存一份可能漂移的 active 状态。来源事件/原始 before/after 不可因退款被重写；退款状态单独记录 ACTIVE/RESERVED/REVOKED 和对应 attempt。

并发重放按每用户稳定顺序读取 baseline、明确 SET、带原始请求数值的 DELTA、关联订单的 PAYMENT_MAX。SET 覆盖，DELTA 按现有规则裁至非负，PAYMENT_MAX 仅在订单权益 active 时生效。已知的语义 no-op 仍需记录，尤其管理员同值 SET、负数裁至 0 的 DELTA、没有提升当前值的支付 MAX。新用户同样必须有 baseline；重放的 projection 更新不能再次生成 SET 事件。

锁序与原流程保持一致：订单 → 期限来源/订阅（订阅退款）→ 用户 → 关联卡按 ID 锁定 → 权益状态。卡消费本来是订阅 → 卡；状态保护放在卡之后，不能反向先锁权益状态再等卡。月度发放持有订单锁，因此退款预占后不能偷发新的关联赠卡。

审核报价绑定实际赠卡使用数、来源 ID/数量/有效期、月度发放状态和并发来源版本。提交时在同一事务重新验证，建立现有退款 attempt 并预占附加权益，然后才允许调用渠道。UNKNOWN 保留预占并用同一退款身份继续查询；确定失败自动释放；成功幂等回收。

## 历史和兼容

历史卡来源可按现有 payment_order_id，或 schedule_issuance_id → issuance → schedule 的外键事实补全。没有来源的卡不推断归属；单独购买 reset_card 订单不冒充订阅赠卡。

缺失的历史并发 before 不伪造。对有限、明确属于升级前的历史订单，保守模式只能在锁定用户后确认当前数值已高于该单目标，并保留当前并发；标明历史 before 未知，不合成 PAYMENT_MAX。其他不完整来源系统自动拒绝，而不是提供跳过回收的退款旁路。新订单缺快照不能使用该历史兼容路径。

API-key auth 缓存含并发字段，仅删缓存不足以阻止旧值写回。启用自动并发回收前须有严格 admission/cache fence，并覆盖并发 0 表示无限制的原语义和 Live/WS 路径。已有请求不强制中断，后续准入使用正确限制。

首次自动回收启用必须与旧进程排空、退款回滚 readiness 和 canonical 发布衔接，不能假设旧 WebSocket 已随 Caddy 切流退出。精确 activation 方案与最终数据表/函数名待实现收敛后补录。

## 验证与发布

必须有真实 PostgreSQL 用卡/退款竞态、重复回调、UNKNOWN/失败恢复、月度发放、后续管理员 SET/兑换 DELTA/其他订单、旧数据兼容，以及缓存旧值写回的验证。源码独立 QA/Review 后执行同源 CI、备份隔离恢复、固定制品发布和健康检查。

中央每日退款不限额必须显式 opt-in；历史默认 0 继续原来的禁止行为，不能因此放宽其他产品。只修改两条授权的 Sub2 live binding，保留 QPS、收款限额现状和全部金额/范围/幂等边界。

中央与 Sub2 都由 root 执行最终发布；子任务不得执行真实退款。此次系统测试不会替用户向历史订单实际退钱。

## 前向发布补充

全站drain不是首次暂停退款的必要条件。先通过root维护锁下的forwardpause guard证明唯一旧writer、准确Caddy/镜像、零退款预占，再在数据库现有advisory lock内CAS reviewed-refund gate true→false；普通HTTP/WS保持accepting。此后canonical蓝绿切流，旧进程自然排空，全部旧writer退出后用原enable helper校验新镜像和readiness，再CAS false→true。

未知原始并发UPDATE必须记为UNATTRIBUTED，不能冒充绝对管理员SET；否则新支付MAX之后旧writer加一会固化全部付费权益。退款来源之后存在未知事件时自动拒绝，不凭目标/现值反推历史。来源之后没有未知事件的新订单仍按可证明事件重放。
