# 支付权益与账户并发设计

## 目标

购买订阅套餐或配置好的充值档位后，账户的并发上限应在支付履约完成时变更到套餐/档位声明的目标值。例如默认并发为 3，购买 `5X PRO` 后并发变为 5。重复支付回调、履约租约恢复和多实例并发执行都不能造成重复发放或把值改乱。

## 语义

- `PlanEntitlements.concurrency` 是购买后的最低目标值，`0` 表示该商品不调整并发；支付履约以原子 `concurrency = max(concurrency, target)` 应用。它不是增量，重复执行安全，也不会让晚到的低档订单或管理员已有更高额度把用户降级。
- 充值档位的 `concurrency` 使用相同语义。只有订单金额与**当前启用的**后台充值档位精确匹配时才会把该权益写入订单快照；手工输入、停售或其他金额不会凭空获得并发权益。
- 订单创建时保存完整商品快照，后续管理员修改套餐或充值配置不会改变已经付款订单应获得的权益。
- 本阶段只允许支付权益单调提高当前 `concurrency`，会一直保持到管理员人工调整。订阅过期后的“恢复基础并发/多个订阅取最大值”需要独立的权益账本与重算任务，不能通过简单减法实现，后续单独扩展；在账本落地前，含并发权益的订单不允许自动退款，避免退款后权益残留。

## 履约与高可用

支付成功后的关键数据变更仍在数据库履约路径中完成：

1. 订单状态使用现有 CAS + 租约（`PAID/FAILED -> RECHARGING`），只有持有租约的实例执行履约。
2. 订阅权益在现有订阅分配事务中写入；充值权益在余额兑换成功后用独立事务写入。两者都以订单审计记录的唯一键作为幂等门，并使用原子 `max(current, target)`，崩溃恢复时重试不会重复增加或降低并发。
3. 写用户并发、余额、累计充值和 RPM 的数据库触发器将 API Key 认证缓存失效事件事务性写入现有 `auth_cache_invalidation_outbox`。提交后再做一次本地/Redis即时失效，降低首个请求读到旧快照的概率；缓存故障仅告警，不能把已完成的履约标成失败。
4. 认证缓存 outbox worker 负责 claim、租约、重试、退避、二次安全 pass 和跨实例 Pub/Sub；它是持久化队列，不依赖进程内 channel。Redis/邮件等非关键副作用可以异步，不能替代上述数据库履约。

## 为什么不把并发写入放进普通 MQ

普通内存队列会在进程退出、网络抖动或消费者异常时丢失消息；即使是 Redis 队列，也必须先做事务性 outbox、幂等键、租约、重试和死信处理，否则会出现“已扣款但权益未落库”。权益落库由订单状态机、数据库事务和审计唯一键保障；现有 outbox 只负责缓存失效的最终送达。并发目标值是一条数据库更新，事务内完成通常是毫秒级，不会造成可感知的支付等待。真正适合异步的是缓存失效、通知、指标和周期性对账。

## 失败与恢复

- 回调重复：订单状态 CAS 或权益审计唯一键挡住重复执行。
- 履约实例崩溃：租约过期后另一实例接管；绝对设置可安全重试。
- 数据库提交成功但 HTTP 回调超时：支付渠道重试仍得到幂等成功。
- 数据库提交成功但 Redis 不可用：outbox 保留事件并退避重试；认证缓存最多在安全窗口后收敛。
- 充值金额未命中或命中停售档位：只发余额，不调整并发。

## 后续扩展

若要支持订阅到期自动降级、多个有效订阅取最大并发、退款回滚或永久充值并发加成，应新增独立的 `user_entitlement_grants` 账本（订单唯一键、类型、目标值、起止时间、撤销状态），并由重算器以“管理员基础值 + 有效权益”计算有效并发；不要在当前 `users.concurrency` 上做减法。Claude 独立审查已要求这个账本作为下一阶段的前置条件。
