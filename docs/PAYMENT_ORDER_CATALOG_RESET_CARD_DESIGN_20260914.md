# 订单、商品目录与重置卡改造设计（2026-09-14）

## 目标

本次改造解决五个相互关联但发布风险不同的问题：

1. 订单管理只保留订单事实与发票状态，发票处理统一进入独立开票队列。
2. 退款审核展示真实状态，采用结构化退款原因，为后续用户自助退款复用同一原因契约。
3. 订阅套餐与余额充值档位统一到后台“商品配置”入口。
4. 重置卡绑定明确的订阅等级，服务端执行“高等级来源卡可用于低等级订阅，低等级来源卡不可用于高等级订阅”。
5. 季付、年付套餐按订阅期起点的日历月锚点逐月发卡，并保证重复回调、重启和多实例并发下不重复发放。

## 退款问题结论

订单 3 的 `LEGACY_SUBSCRIPTION_UNATTRIBUTED` 与 0.01 元测试价格无关。该订单没有 `payment_subscription_grants` 记录，系统无法证明实际开通的订阅 ID、期限起止和当前可退款尾段，因此在计算比例前就进入人工审核。

人工审核响应没有现金报价，旧前端把缺失数值当成零，才显示了误导性的 `¥0.00`。正确行为是显示“退款金额待人工核算”，同时保持确认按钮禁用。不能从商品标称天数或当前订阅到期时间倒推历史期限。

若未来要让订单 3 进入自动退款，必须先依据支付、履约和订阅变更记录做一次订单级审计回填；不能复制订单 4 的回填数据。正常且具有期限凭据的 0.01 元订单仍会执行既定的最小货币单位取整规则。

本次产品决定为“只允许审计回填”：对于无法证明订阅期限的历史订单，继续保持 `can_refund=false`，不提供“仅退现金、订阅权益不自动回收”的人工旁路。审计回填必须记录订单、证据来源、回填前后值、操作者和时间，回填完成后再重新生成退款审核报价。

退款原因采用以下稳定代码，直接复用统一支付网关的原因枚举：

| 代码 | 管理端含义 |
| --- | --- |
| `customer_request` | 用户主动取消 |
| `duplicate_charge` | 重复扣款或重复购买 |
| `service_not_delivered` | 服务未交付 |
| `service_error` | 服务异常 |
| `other` | 其他；必须填写补充说明 |

原因代码与单行摘要随退款 attempt 持久化。网关重试必须读取同一份持久化值，不能在重试时重新生成原因。

## 商品配置决策

不重写订单和商品持久化。后台建立统一“商品配置”门面：

- “订阅套餐”继续读写 `subscription_plans`，订单继续保存不可变 `product_snapshot`。
- “余额充值”继续读写经过服务端校验的 `PAYMENT_RECHARGE_OPTIONS`。
- 支付渠道、费率、订单超时和支付能力仍属于技术性的“支付设置”。
- `entitlements.balance_bonus` 在订阅表单中明确标为“随套餐赠送余额”，它不是余额充值商品。

这样可以统一管理员的产品操作入口，同时保留上游经过验证的支付、履约、退款和历史订单契约。

## 重置卡等级契约

套餐名称和价格不是权限依据。每个订阅产品分组必须配置稳定的卡类型 `family_key` 和正整数等级 `tier_rank`。订单和每批卡保存购买时的不可变等级快照。

服务端唯一兼容判定为：

```text
grant.family_key == current_subscription.family_key
&& grant.source_tier_rank >= current_subscription.tier_rank
```

因此按用户指定规则：

| 当前订阅 | Plus 来源卡 | 5X 来源卡 |
| --- | --- | --- |
| Plus | 展示并可使用 | 展示并可使用 |
| 5X | 不返回、不展示、拒绝使用 | 展示并可使用 |

旧卡没有等级快照，只能继续用于原 `subscription_id`，不能自动获得跨套餐权限。未配置等级的新品购买也保持原订阅精确绑定，避免迁移瞬间放宽权限。

列表接口和消费事务必须执行同一判定。前端隐藏只是体验优化，不能作为安全边界。购买确认页明确提示“卡仅适用于当前等级及更低等级；升级到更高等级后不会展示且不能使用”。

等级策略首次创建也属于并发边界。策略写入先对订阅分组父行加 `FOR UPDATE`，购买、套餐快照和管理员发卡先按分组 ID 升序对同一父行加 `FOR SHARE`，再读取可选的等级策略行。迁移触发器对旧版本省略快照字段的 SQL 执行同一锁序并固化快照。`tier_snapshot_resolved` 区分旧 SQL 的省略值和新代码明确冻结的 exact-only 值，因此延迟履约和未来月度期次不会被后来启用的策略改写。分组、family、rank、来源套餐和解析标记在发卡后均不可修改。

## 逐月发放契约

按月发放只应用于启用该模式的新订单，旧订单和已发卡不追溯拆分。

- 计划明确保存每期数量、总期数和 `monthly` 发放模式，不能用 90/365 除以 30 推断期数。
- 锚点使用订单对应订阅 term 的 `term_start_at`，不能使用异步支付回调到达时间。
- 每次日期都从原始锚点计算。月末购买采用月末夹取规则，例如 1 月 31 日对应 2 月末、3 月 31 日。
- 第一期在 term 开始时发放；续费订单的 term 尚未开始时不得提前发卡。
- 每批有效期不晚于下一发放边界和该订单 term 结束时间。
- 调度表通过 `(schedule_id, issue_index)` 唯一约束保证幂等；多实例 worker 使用现有 leader lease，并在数据库事务中锁定到期 schedule。
- 宕机恢复时跳过已经结束的月度窗口，不能把错过月份积攒成一批长期可用卡。
- 订阅被缩短、删除或停用后停止后续发放。含重置卡权益的订单仍保持人工退款复核，直至退款账本能安全撤销已发卡和未发 schedule。
- `FAILED`、`RECHARGING` 和退款处理中等可恢复状态只暂停当前窗口，不取消计划或消耗期次；管理员重试只重整月度账本。`CANCELLED`、`EXPIRED`、最终退款、权益凭据缺失、订阅失效或当前 term 不再覆盖下一期才永久取消。

## 交付任务与门禁

| 任务 | 依赖 | 验收条件 | 发布边界 |
| --- | --- | --- | --- |
| T1 订单页发票入口清理 | 无 | 订单页无处理入口；状态和筛选保留；独立队列可用 | 普通前端变更 |
| T2 退款展示与结构化原因 | 无 | 人工审核不显示 0；五类原因可审计；旧请求兼容；重试原因不漂移 | 金融迁移后端先行 |
| T3 统一商品配置入口 | 无 | 套餐和充值档位同页分区；充值编辑从设置移除；两类原存储不变 | 普通前后端变更 |
| T4 重置卡等级绑定 | T3 | Plus/5X 双向矩阵测试；旧卡 exact-only；服务端列表和消费同规则 | 数据迁移和代码同时生效 |
| T5 月度发卡调度 | T4 | 3/12 期、月末、闰年、重启、双 worker、提前终止均通过 | 独立运行栅栏与观测 |
| T6 独立 QA 与代码审查 | T1-T5 | 聚焦测试、完整测试、迁移检查、权限绕过检查无阻断项 | 发布前必过 |

T1、T2、T3 可在同一版本中独立验证。T4 涉及资格模型和历史兼容，应在迁移完成后再开放等级配置。T5 引入后台调度，应单独设置启用开关、指标和回滚路径；在 worker 未启用时不允许管理员保存新的 `monthly` 套餐。

## 上线与启用顺序

1. 依次执行迁移 247、248、249，再发布后端和前端；迁移均先扩展字段与表，不回写或放宽旧卡权限。
2. 确认所有实例已完成迁移并排空旧版本后，再为在售订阅配置和核对 `family_key`、`tier_rank`，随后开放带等级快照的新重置卡商品。数据库触发器在滚动窗口内兼容旧 SQL，但不能替代发布完成确认。已经产生等级快照、月度计划或商品订单后，相关等级策略冻结，不能原地改写历史语义。
3. `monthly_reset_cards_enabled` 默认关闭。确认 worker leader lease、到期扫描和失败重试正常后再开启；关闭开关会阻止新月度商品展示和购买，但已付款并已建立的计划仍继续履约。
4. 历史退款订单只通过带证据和操作者记录的审计回填恢复报价；本版本不提供跳过权益回收的现金退款旁路。
