# 订单、商品目录与重置卡改造设计（2026-09-14）

## 目标

本次改造解决五个相互关联但发布风险不同的问题：

1. 订单管理只保留订单事实与发票状态，发票处理统一进入独立开票队列。
2. 退款审核展示真实状态，采用结构化退款原因，为后续用户自助退款复用同一原因契约。
3. 订阅套餐与余额充值档位统一到后台“商品配置”入口。
4. 重置卡绑定明确的订阅等级，服务端执行“高等级来源卡可用于低等级订阅，低等级来源卡不可用于高等级订阅”。
5. 季付、年付套餐按订阅期起点的日历月锚点逐月发卡，并保证重复回调、重启和多实例并发下不重复发放。

## 退款问题结论

订单 3 的 `LEGACY_SUBSCRIPTION_UNATTRIBUTED` 与 0.01 元测试价格无关。该订单在 2026-09-14 引入 `payment_subscription_grants` 的迁移 245 和新版履约写入逻辑之前完成，因此只有旧的订阅开通记录，没有订单级期限凭据。系统无法证明实际开通的订阅 ID、期限起止和当前可退款尾段，所以在计算比例前就进入人工审核。

人工审核响应没有现金报价，旧前端把缺失数值当成零，才显示了误导性的 `¥0.00`。正确行为是显示“退款金额待人工核算”，同时保持确认按钮禁用。不能从商品标称天数或当前订阅到期时间倒推历史期限。

若要让订单 3 进入自动退款，必须先依据支付、履约和订阅变更记录做一次订单级审计回填；不能复制订单 4 的回填数据。迁移 245 之后的新订阅订单会在履约事务中写入 `payment_subscription_grants`，失败则不会被标记为成功履约，并由既有恢复流程继续处理；因此正常新订单不会再以这一历史原因缺少期限凭据。正常且具有期限凭据的 0.01 元订单仍会执行既定的最小货币单位取整规则。

本次产品决定为“只允许审计回填”：对于无法证明订阅期限的历史订单，继续保持 `can_refund=false`，不提供“仅退现金、订阅权益不自动回收”的人工旁路。审计回填必须记录订单、证据来源、回填前后值、操作者和时间，回填完成后再重新生成退款审核报价。

生产备份显示订单 3 和订单 4 共用订阅 `1`：订单 4 已有的不可变 grant 覆盖 `2026-10-12 15:13:43Z` 至 `2026-11-11 15:13:43Z`，因此订单 3 的审计表单只能建议其前一段未占用的 30 天，不能再次建议订阅尾部。审计 revision 同时包含现有 grant 区间，提交前若期限占用发生变化必须刷新。订单 4 的退款预占尚未终结时，订单 3 即使完成 provenance 回填也不能再建立第二个订阅退款预占；必须先让订单 4 的同一退款请求完成或安全释放，再由服务端生成订单 3 的实时比例报价。

退款原因采用以下稳定代码，直接复用统一支付网关的原因枚举：

| 代码 | 管理端含义 |
| --- | --- |
| `customer_request` | 用户主动取消 |
| `duplicate_charge` | 重复扣款或重复购买 |
| `service_not_delivered` | 服务未交付 |
| `service_error` | 服务异常 |
| `other` | 其他；必须填写补充说明 |

原因代码与单行摘要随退款 attempt 持久化。网关重试必须读取同一份持久化值，不能在重试时重新生成原因。

## 商品配置决策

不重写订单和商品持久化。后台建立统一“商品配置”门面：

- “订阅套餐”继续读写 `subscription_plans`，订单继续保存不可变 `product_snapshot`。
- “余额充值”继续读写经过服务端校验的 `PAYMENT_RECHARGE_OPTIONS`。
- 支付渠道、费率、订单超时和支付能力仍属于技术性的“支付设置”。
- `entitlements.balance_bonus` 在订阅表单中明确标为“随套餐赠送余额”，它不是余额充值商品。

这样可以统一管理员的产品操作入口，同时保留上游经过验证的支付、履约、退款和历史订单契约。

## 重置卡等级契约

套餐名称和价格不是权限依据。项目通过版本化迁移为受支持的订阅产品绑定隐藏且不可变的 `subscription_product_code`，并在系统表中维护卡类型 `family_key` 和正整数等级 `tier_rank`。当前内置 Plus=`openai_plus`/等级 1、5X Pro=`openai_5x`/等级 2；后台不提供编辑入口。订单和每批卡保存购买时的不可变等级快照。

服务端唯一兼容判定为：

```text
grant.family_key == current_subscription.family_key
&& grant.source_tier_rank >= current_subscription.tier_rank
```

因此按用户指定规则：

| 当前订阅 | Plus 来源卡 | 5X 来源卡 |
| --- | --- | --- |
| Plus | 展示并可使用 | 展示并可使用 |
| 5X | 不返回、不展示、拒绝使用 | 展示并可使用 |

旧卡没有等级快照，只能继续用于原 `subscription_id`，不能自动获得跨套餐权限。未配置等级的新品购买也保持原订阅精确绑定，避免迁移瞬间放宽权限。

列表接口和消费事务必须执行同一判定。前端隐藏只是体验优化，不能作为安全边界。购买确认页明确提示“卡仅适用于当前等级及更低等级；升级到更高等级后不会展示且不能使用”。

等级策略由版本化迁移写入并校验冲突。购买、套餐快照和管理员发卡先按分组 ID 升序对父行加 `FOR SHARE`，再读取系统等级行；迁移触发器对旧版本省略快照字段的 SQL 执行同一锁序并固化快照。`tier_snapshot_resolved` 区分旧 SQL 的省略值和新代码明确冻结的 exact-only 值，因此延迟履约和未来月度期次不会被后续版本改写。分组、family、rank、来源套餐和解析标记在发卡后均不可修改。

## 逐月发放契约

按月发放只应用于启用该模式的新订单，旧订单和已发卡不追溯拆分。

- 计划明确保存每期数量、总期数和 `monthly` 发放模式，不能用 90/365 除以 30 推断期数。
- 锚点使用订单对应订阅 term 的 `term_start_at`，不能使用异步支付回调到达时间。
- 每次日期都从原始锚点计算。月末购买采用月末夹取规则，例如 1 月 31 日对应 2 月末、3 月 31 日。
- 第一期在 term 开始时发放；续费订单的 term 尚未开始时不得提前发卡。
- 每批有效期不晚于下一发放边界和该订单 term 结束时间。
- 调度表通过 `(schedule_id, issue_index)` 唯一约束保证幂等；多实例 worker 使用现有 leader lease，并在数据库事务中锁定到期 schedule。
- 宕机恢复时跳过已经结束的月度窗口，不能把错过月份积攒成一批长期可用卡。
- 订阅被缩短、删除或停用后停止后续发放。含重置卡权益的订单仍保持人工退款复核，直至退款账本能安全撤销已发卡和未发 schedule。
- `FAILED`、`RECHARGING` 和退款处理中等可恢复状态只暂停当前窗口，不取消计划或消耗期次；管理员重试只重整月度账本。`CANCELLED`、`EXPIRED`、最终退款、权益凭据缺失、订阅失效或当前 term 不再覆盖下一期才永久取消。

## 产品规则修订（2026-09-15）

以下规则来自管理员完成首轮线上验收后的明确修订，覆盖本文较早的可配置等级策略与全局月度开关设计。

### 退款审核与权益状态

- `RF-01`：退款进入处理中后，订单详情必须显示本地退款 attempt、是否已经取得网关退款 ID、最近一次自动对账时间及可安全公开的状态说明；管理员可以触发同一 attempt 的查询，不得创建第二笔退款。
- `RF-02`：`LEGACY_SUBSCRIPTION_UNATTRIBUTED` 必须在退款对话框提供“审计回填”入口，明确列出需要核对的订阅、期限和证据。审计回填完成后重新生成服务端报价；管理员不能绕过期限证据直接填写任意现金退款金额。
- `RF-03`：订单列表继续保留“权益曾经成功发放”的历史事实，同时单独展示退款后的权益处理结果：已回收、回收中、历史未回收或需人工处理，不能用“已发放”掩盖退款后的当前权益状态。

### 套餐内置月度发卡

- `RC-01`：月度发卡是系统默认能力，不再提供全局启用开关。后台创建或编辑套餐时直接选择“一次发放”或“按月发放”。
- `RC-02`：一次发放模式填写本订单一次发放的总张数；按月发放模式填写每个日历月发放的张数，系统根据套餐明确的期限单位计算总期数并展示预览。
- `RC-03`：两种模式都必须允许选择单张重置卡的有效期数值与单位。每批卡的实际到期时间仍不能晚于订阅 term 结束时间；按月发放还不能晚于下一期边界。
- `RC-04`：调度器默认运行，但只通过到期索引取有限批次并由单 leader 处理；没有到期计划时为常数级空查询，不为用户创建独立定时器，也不扫描全部订单或订阅。

### 系统内置等级兼容

- `RC-05`：“重置卡兼容等级”不再作为管理员配置项或公开写接口。当前项目内置同一 GPT 卡类型中的等级顺序：Plus 为低等级，5X Pro 为高等级；5X Pro 来源卡可以用于 Plus，Plus 来源卡在 5X Pro 订阅中不返回、不展示且拒绝使用。
- `RC-06`：等级判定继续由服务端列表与消费事务共同执行，并在订单与卡批次中保存不可变来源快照。项目新增或改变订阅等级需要通过版本化迁移和代码审查，不允许管理员在线改写已经发卡的历史语义。
- `RC-06a`：迁移在数据库层冻结内置产品代码和 Plus/5X 等级行，阻止滚动发布期间仍存活的旧管理接口改写系统规则；后续调整只能由新的版本化迁移显式替换保护触发器。
- `RC-07`：迁移前没有等级来源快照的旧卡继续保持原订阅精确绑定，不因本次默认规则获得跨套餐权限。
