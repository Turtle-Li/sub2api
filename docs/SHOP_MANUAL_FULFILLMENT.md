## 商品配置与入口

- 用户入口 `/shop`；后台商品配置 `/admin/shop/products`；人工队列 `/admin/shop/orders`。既有用户/管理员订单列表也可进入商城订单。
- 商品可配置名称、自由分类、简介、Markdown 详情、人民币价格、期限数值/单位、交付模式、资料格式/获取地址/说明、教程、排序和上架状态。
- 默认期限 1 个月、未上架、价格 0。没有预置公开商品、价格或库存；上架必须有有效价格。编辑使用 revision，历史订单保存独立商品快照。
- 价格内部以人民币分保存；仅专用商城接口按服务端商品价格创建 `manual_shop` 订单。浏览器不提交金额、用户 ID 或交付状态。沿用支付宝/微信统一收银台及原订单恢复机制。
- 支付方式以 checkout-info 实际返回的支付宝/微信键为准，`available` 是可选字段，仅明确 false 时禁用；商品金额还须符合该方式的人民币单笔范围。不得因字段缺失隐藏正常渠道，也不得凭空展示未配置渠道。案例见 `docs/bugs/frontend/BUG-20261104-shop-payment-methods.md`。
- 商城不发放 API 余额、订阅、重置卡或返佣；充值倍率、充值手续费和余额开关不改变商城商品金额。
- 购买详情展示一次“5分钟–2小时操作完成，着急可联系客服”；简介或详情已包含相同时效时，不再叠加系统提示。商城列表及订单页不重复时效横幅。代充从付款且提交完整资料后安排人工处理，客服沿用站点 `contact_info`。

## 人工流程

| 模式 | 付款后 | 管理员操作 | 买家结果 |
| --- | --- | --- | --- |
| `session_topup` | 待提交资料 | 复制完整资料、开始处理、站外代充、确认完成；必要时请求补充资料 | 订单完成和邮件通知 |
| `account_delivery` | 待人工处理 | 填写完整账号资料、预览、确认发货 | 自己的订单查看/复制资料，并收到完整资料邮件 |

成品号支持单条 `账号----密码` 专项展示。后台粘贴后预览，买家分别复制账号、密码，不再重复提供完整原文复制按钮；密码保留第一个分隔符后的全部内容，不猜测多行格式。识别不修改提交原文、邮件或版本字段，也不作用于 API Key 交付。未拆分的文本及 API Key 保留完整复制。使用前必看入口保留，指南提供固定目录、手机章节选择和返回原订单/商品入口。

代充引导买家先登录要充值的 ChatGPT 账号，再在同一浏览器访问 `https://chatgpt.com/api/auth/session`，复制全部内容并提交。粘贴或编辑 JSON 后，浏览器立即在本地提取名称、邮箱、订阅类型和 Session 有效期，提示不完整内容、过期或账号不一致；不自动发送请求，不存储原文或解析结果，清空输入即清除预览。Session/令牌到期时间不是订阅到期时间，资料未提供的信息显示未知。点击一次“提交”后顺序完成服务端初检与保存，检查接口不保存资料或改变订单；页面不再另设重复确认步骤。服务端检查有效邮箱、JWT 结构、令牌与 Session 的有效期，以及存在时的邮箱、用户和工作区一致性。本地提示不代替服务端判断；订阅类型缺失或不一致仅提示人工核对，不据此自动决定充值资格。管理员可为其他商品配置 HTTPS 地址及文本格式，文本商品不运行 Session 解析。内容保留原始字节，不做重新序列化。

初检只解析提交资料，不验证 JWT 签名、不调用第三方、不证明官方当前订阅状态。仅单笔本人/管理员订单返回邮箱、订阅枚举和最早到期时间；列表和通知不增加资料摘要，原始令牌不回显。完成代充按资料提交时刻校验，避免令牌在站外操作后过期导致无法登记已完成结果。实际样例只用于本地确定字段结构，测试使用合成资料。

付款状态与人工履约是独立持久事实。付款可信回调只将人工单放入队列，不运行自动权益发放；只有管理员确认完成才完成履约。履约状态为 `WAITING_PAYMENT / WAITING_INPUT / QUEUED / PROCESSING / NEEDS_INPUT / COMPLETED / CLOSED`。取消、过期和退款等资金状态显示为已关闭，筛选使用相同有效状态，先筛选再统计和分页。

所有写入按 `payment_orders → shop_fulfillments` 加锁，带 revision；完成代充还校验 input_revision。开始处理后买家不能修改资料；请求补充时清除旧 Session。重复/并发确认只完成一次，并在同一个事务里更新资金订单、履约、清除 Session、写入邮件任务。

资料页始终以 `can_submit` 决定是否提供编辑能力：排队期间允许更新时，放在默认折叠的“更新充值资料”入口中；开始处理后不再提供输入框。检查和提交继续发送完整原文，成功后清空输入。

常规商城退款须人工售后核对，专用服务明确拒绝套用余额/订阅退款回收；不扣 API 余额。取消后晚到的可信付款沿用既有统一支付退款安全流程，不进入人工发货。已有付款/退款复核栅栏会阻止复制资料与履约操作。不得另加绕过该栅栏的按钮。

## 资料与通知边界

- Session 和交付信息采用现有 AES-GCM 加密器，密文绑定订单、用途和版本。商城要求配置持久 `TOTP_ENCRYPTION_KEY`，缺失时拒绝购买及敏感操作；配置继续按项目 Vault/部署规范管理，文档和仓库不存密钥。
- Session 仅当前管理员 JWT 的专用 reveal 接口返回；管理员 API Key 均不能访问商城管理，沿用站点已配置的 step-up。所有商城响应带 `no-store, private`。资料提交/复制/交付请求体不进入审计原文，错误不回显原文。
- 提交成功或离开编辑页清空浏览器文本；Session 不存 localStorage、邮件或飞书。完成代充、请求补充资料时清除 Session 密文。
- 账号信息仅完成订单的 owner 详情返回，管理员订单列表/详情/动作响应均不回传交付明文。买家页面默认遮挡，支持显示、整份复制及逐行复制。邮件正文对所有用户资料做 HTML 转义。
- 飞书沿用站点现有配置，只含订单/商品/金额/状态/后台链接，不含 Session、账号交付信息或目标邮箱。付款及提交资料分别产生管理员通知任务。
- 邮件使用现有 SMTP，完成交付与请求补充资料产生邮件任务；成品号邮件含交付原文及教程入口。
- 通知独立持久化为 outbox，租约认领、退避重试、过期租约恢复。失败不回滚完成状态；管理员可重试通知，不能因此再次发货。SMTP 是至少一次投递，服务在发送成功但写回前崩溃可能重复邮件，不承诺“恰好一次”。
