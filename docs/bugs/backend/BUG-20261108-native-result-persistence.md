# Native image storage failures and result-persistence reliability

## Evidence and boundary

The controlled native acceptance on tariff-aware runtime4f1f86ef created exactly
five one-image jobs with existing owner key127. Muse and Seedream Lite completed
and settled at0.10 and0.32. Seedream Pro job
`imgbatch_933500f9daae62b1e33f1faa68ba0a34` logged
`batch_image.provider_status_check_failed`, HTTP503
`BATCH_IMAGE_PROVIDER_STORAGE_UNAVAILABLE`. A durable upstream-attempt marker
existed on the next invocation. Its synchronous Resume refused replay; the final
item reported `synchronous bridge attempt outcome unknown; replay forbidden`.
The job settled at0 with one failure. No duplicate POST was issued.

The log does not identify which conditional write failed: the initial attempt
claim can also be committed without an acknowledgement. It therefore cannot
prove whether the upstream received the Pro request or produced an image. Do not
describe this canary as a confirmed successful generation or a passed channel.

Separately, the common provider stores a finished result once in `putResultLine`. An error
returns out of the worker with the result bytes no longer available on the next
invocation. For a synchronous provider that invocation cannot safely generate
again. The storage service's exact initial failure cause is unavailable because
conditional Put currently discards its sanitized SDK diagnostics. This evidence
motivates a directly reproduced result-persistence reliability defect, not a
proven diagnosis of the canary's exact failing operation or a credentials defect.
The unknown attempt cannot be recovered by replay.

## Repair and checks

Keep the generated bytes in the current invocation for at most three attempts
to create the same conditional result object, with cancellation-aware250/500ms
delays. Each retry resets the in-memory reader. First-writer semantics remain
authoritative, including when the first write succeeded but its acknowledgement
was lost. Do not retry the upstream-attempt claim or any generation POST.

Reuse existing sanitized COS operation diagnostics for a failed conditional
write; expose status/code/category, never URLs, response bodies or secrets.

Regression cases: two failed result saves followed by success with exactly one
upstream call; lost write acknowledgement followed by an existing object;
cancellation; permanently failing storage stops after three attempts. COS tests
retain atomic create/versioning guards and reject sensitive diagnostic content.
