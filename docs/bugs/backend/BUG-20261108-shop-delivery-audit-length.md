# 自动交付已创建 Key 但商城不能完成订单

状态：ANALYSIS_READY；2026-11-08，来源为买家实际购买后的交付延迟反馈。

## 现象与证据

- 订单72于 `2026-11-08T11:15:53Z` 付款，接收端于 `11:16:05Z` 创建唯一有效授权。
- 商城仍为 `PAID / PROCESSING / RUNNING`；截至 `11:24:26Z` 已尝试6次。
- PostgreSQL每次处理都记录 `value too long for type character varying(50)`，时间与商城交付失败日志一一对应。
- 实际动作ID长44字符；`SHOP_ACTION_COMPLETE_` 加ID为65字符，而生产 `payment_audit_logs.action` 为 `VARCHAR(50)`。没有读取或记录实际 Key、交付密文及买家个人资料。

## 调用链与根因

可信付款 → 事务 outbox → 20秒扫描领取 → 接收端幂等创建/获取原 Key →
`completeShopAction` 加密交付并更新完成状态 → 写入超长审计 action → 整个本地完成事务回滚。
任务保留 RUNNING，90秒租约过期后重新领取，因此看起来一直在交付。

同类缺陷还影响 `finishShopRevocation` 和管理员重试/撤销的审计标识。原始动作、
快照、付款和接收端幂等回执均未丢失。原付费时钟不变，不能重新创建或延长授权。

此前真实 PostgreSQL 测试通过 Ent 建表；Ent 的字符串 MaxLen 校验没有把该测试数据库列
建成生产迁移093的 VARCHAR(50)，而审计使用原始SQL，未经过Ent字段校验，遗漏了此约束。

## 推荐修复与验收

1. 每个订单仅有一个不可变交付动作：完成/撤销使用固定事件名；管理员操作使用事件名与
   claim revision。完整动作ID继续保留在审计 detail，不截断ID，不更改历史审计或数据库结构。
2. PostgreSQL 集成环境明确使用生产50字符限制，复现失败后验证完成、管理员重试/撤销、
   回执幂等、原付费时钟和通知只入队一次。
3. 发布兼容修复，由原任务自然恢复订单72；只读核对完成状态及原接收端授权身份。
4. 后续交互修复应使订单状态自动刷新；20秒兜底扫描的常规排队耗时与本次事务失败分开验证。

风险：审计事件幂等键变化。以单订单唯一动作及递增 claim revision 保证原有幂等/历史可追踪；
保留资金、退款、撤销和加密授权边界。无需迁移、手工改金融状态或操作接收端授权。

knowledge_candidate: yes；生产字段约束必须进入真实数据库回归，项目内保留该缺陷证据。
