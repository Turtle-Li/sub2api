The GoodPut Videos API sends both images as `media` entries with `type: first_frame` and `type: last_frame`. The role table and example do not show Fast, so the Fast-specific model card is separate evidence, not a substitute for a real Fast result. An accepted request or returned task ID is not evidence that both images control the final video.

GoodPut's public catalog on 2026-11-19 returned both models at CNY 0.09 per billable second (listed regular price CNY 0.50), and no public Seedance listing. This is an upstream cost, not the Sub2 wallet price. At that rate, 5/10 seconds cost CNY 0.45/0.90, and 400–700 billable seconds cost CNY 36–63 before creative retries. [MiniMax's mainland API price list](https://platform.minimax.cn/docs/pricing/overview) lists H3 at CNY 0.50 per output second at 768P. GoodPut describes its Fast tier as a different compute queue for the same H3 model, not the official Highspeed/Lite tier. The source contract is GoodPut's [Videos API](https://goodputai.cn/zh-CN/docs/video-generation) and [public pricing API](https://goodputai.cn/zh-CN/docs/public-api). The separate Ark [Seedance](seedance-api.md) path, Grok, and native Muse keep their own protocols and accounts. Shared account admission, task ownership and per-second usage follow the Sub2 media path at baseline `5fe2f8486fd36446b2fa4381fbe90f188b571c82` (`backend/internal/handler/grok_media.go`, `backend/internal/service/grok_media.go`, `backend/internal/handler/grok_media_slots_test.go`).

The pilot supports JSON text-to-video, first/last frames and reference URLs/inline data URLs through `media` or `input_reference`. Do not mix frame inputs with `reference_*` inputs. Default duration is 5 seconds. Only Fast accepts `seed`. Binary multipart input is not enabled for the pilot. The adapter does not fetch client-supplied asset URLs; use non-sensitive, publicly reachable references with enough expiry for queue time.

- `POST /v1/videos` returns a `gpv_` task ID after the owner, account and pending usage metadata are recorded. Ambiguous submissions are not replayed and have no fallback.
- `GET /v1/videos/{id}` returns the normalized state. For a completed task, `usage.duration_seconds` is the verified billable duration when available, not a measurement of the MP4. A missing or inconsistent meter does not hide `completed` or the download. `GET /v1/videos/{id}/content` returns MP4 using the same Sub2 key. The returned `video_url` is a protected Sub2 relative path; it is not a signed provider URL, and still requires the Sub2 key. No GoodPut key, native task ID, or storage URL is sent to the caller. Do not follow provider redirects with a credential.
- Only the creating user, key, group and originally selected account may read a task, for 24 hours. Read access does not depend on `is_exclusive` or on remaining balance or Key quota. Revoked access, expired Keys and all ordinary group/account checks still apply. The 720p bucket is a billing key, not an output canvas.
- Before each new submit, the adapter checks the unauthenticated GoodPut catalog for that exact ID, CNY, and a single known seconds meter at or below CNY 0.09. It refuses to submit for a missing/unverifiable price, a new meter, or a higher price. This check is not a locked price from GoodPut. Use a dedicated Key budget, compare the first live bill, and drain tasks before changing Sub2 prices. Existing task reads do not depend on the promotion still being active.

## Durable settlement and public use

Migration 278 creates a PostgreSQL task ledger. Before one upstream POST, the transaction temporarily reserves the rounded maximum quote (no usage charge), checks the Key's quota/windows, and records the original owner, group, model, account and quote. Failed admission sends no GoodPut POST. The active generation checks due receipts using the original account's normal outbound policy and slots, including if the customer's key is no longer active. Migration 280 settles a bound completion at the reported whole seconds inside the model's range and at or below the submission quote. It keeps the original `seconds`, stores `billed_seconds`, and prorates the original pricing snapshot by `billed_seconds / seconds`. Debit, release of the excess reserve, quota updates and one video usage row commit atomically. Verified rejection or failure releases the full hold. Polling/downloading a durable task never charges it. Old pilot receipts still use the same-key, bounded legacy lookup within their original window.

Public submissions are off by default. An exact H3-only wallet group remains the routing requirement. After confirming GoodPut authorization for paid downstream use, configure the existing public H3 group via the normal application config:

```yaml
gateway:
  goodput_video_public_group_id: 46
```

The owner confirmed by email communication with GoodPut that this account may be used downstream and approved opening #46 for normal paid use on 2026-11-20. This approval does not extend to other groups, accounts, or providers.

There is no cumulative trial-seconds budget. Standard H3 accepts 4–15 seconds; Fast accepts 5–15, with 15 sent as 14 per GoodPut's limit. At 0.15 points per billable second, a 15-second standard H3 submission temporarily holds 2.25 points; an actual 14-second meter debits 2.10 and returns 0.15 to available balance. One running or outcome-unknown task per key, wallet/key allowance, and the upstream cost ceiling still apply. Stop new public calls by clearing the configured group ID or disabling media generation for the group while the runtime continues to poll accepted receipts. Drain outstanding holds before promoting a binary that cannot reconcile actual usage, and never restore an older database for an application rollback.

On a transport timeout or missing/invalid acceptance receipt, the pending hold is flagged for review; no POST is replayed. There is no verified upstream idempotency token or guaranteed discovery of a lost receipt. Do not release or force-capture money without checking the GoodPut ledger and task evidence. For a completed task with missing, invalid or over-quote usage, deliver the video but do not guess a charge. The known-completed task no longer occupies the in-flight slot; the still-frozen quote counts against the wallet and Key's limits. The worker checks saved review receipts by GET only, at most once every five minutes and within the 24-hour receipt window. It never replays an uncertain submit or refunds on a missing receipt.

The Ops rule **GoodPut H3 生成或结算异常** creates a P1 event per task and incident type (one task does not suppress others). It detects missing receipts, unverified usage, oldest pending reservations past the configured wait (default 15 minutes), and detected content-read failures not cleared within a minute. The worker does not download every MP4 preemptively. Ops keeps the original incident when an affected job is recovered and sends its initial notification using the existing severity, recipient, silencing and rate-limit settings; an unsent active event is retried on the next evaluation. The event includes the Sub2 task or reservation ID, model and group only; it excludes upstream receipts, media and credentials. Investigate the original ID and provider ledger, then verify the same row's state, `billed_seconds`, stable usage record and release of this particular hold. For a provider duration question, supply the GoodPut request IDs through the published support contact, not the customer Key or media.

For the ordinary-user acceptance test after activation, submit exactly one 5-second two-frame job with a separate low-limit user Key, save the 202 receipt and **do not GET status or content**. Verify one 0.75-point usage row and release of its hold using the platform ledger, then query and download with the original Key and verify no additional deduction. Verify an unrelated Key cannot access the task. Stop on a non-matching GoodPut charge, unknown receipt, or unavailable content.

Local verification uses mocked upstream price, creation, polling, and content replies. No account, payment, deployment, or production configuration is created by these tests. The focused service/handler/route race tests passed with `go test -tags unit -race ./internal/service ./internal/handler ./internal/server/routes -run TestGoodPut -count=1`. The separate locally decoded smoke fixtures are a red cube on the left and a blue sphere on the right; both PNGs and both five-second request bodies were reused for the production checks below.

## Pilot state and first/last-frame acceptance

- At the original smoke, Sub2 group `minimax h3` (#46) was an exclusive, owner-only OpenAI wallet group at 1× with one GoodPut account, media enabled, an exact two-model allowlist, and a price of **0.15 internal points per billed video second**. Image groups are unchanged. The GoodPut adapter is in production at `6c295e9455077e6ed15d821fa83a7d635e3077ef` (release workflow `44678581242`). No customer access was enabled for that smoke.
- Production smoke, 2026-11-20 UTC: only the current administrator was granted #46. A fresh one-day test key was capped at 2 points. The key listed just `minimax/h3` and `minimax/h3-fast`; both catalog meters were CNY 0.09/s before their respective submissions. One five-second job per model returned 202 and completed; there was no paid retry or fallback.
- Both same-key content reads returned a non-redirect MP4. Decoding each yielded 124 frames at 24 fps, 1344×768, approximately 5.17 seconds of video, plus AAC audio. The first decoded frame preserved the red cube on the left; the last preserved the blue sphere on the right. Unauthenticated content access returned 401. This proves endpoint control for this fixture, not visual quality for all content or supported modes.
- The two GoodPut call records each showed 5 billed seconds and CNY 0.45. After polling and both downloads, the Sub2 trial key had exactly two usage rows, one per model at 0.75 points each. Totals: 10 billed seconds, CNY 0.90 upstream, 1.50 Sub2 points. Content reads took about 53 and 34 seconds in this run. This is initial production evidence, not a latency or availability guarantee.
- This original smoke exercised read-triggered settlement, not the new unattended path. It is not evidence that public submissions or unattended settlement are enabled in production.
