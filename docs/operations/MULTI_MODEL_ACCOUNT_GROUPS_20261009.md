# Multi-model accounts in provider groups

## Contract and baseline

User request: OpenCode, Command Code and Cline accounts can bind to existing model-provider groups, including Kimi and DeepSeek. Keep group IDs, keys, rates, quota attribution and native account identity. No database migration or account conversion.

Baseline: `57d741cfaa61bc270e25e71fcd9c887ad6eea30d`, fork/main. Fixed upstream reference: Wei-Shaw/sub2api `f2669c8cf62555cd92389b3f55920e9e6e7c6ff2` (v0.2.15). Relevant upstream contracts: `internal/domain/platforms.go`, `internal/service/{cline,provider_profile,openai_gateway_scheduling,openai_account_scheduler,composite_platform}.go`, their tests, and `frontend/src/components/common/GroupSelector.vue`. Intentional fork difference: these three multi-model providers may serve another provider's group when the resolved upstream model belongs to that group's model family. Existing upstream forwarding profiles, wallet cooldowns and LGPL-3.0 obligations remain in force.

Acceptance criteria:

- AC1: Create/edit can assign each of the three account platforms to model-provider groups without replacing existing keys/groups. Existing exact-platform/composite/Antigravity behavior remains available.
- AC2: Assigned accounts participate in both scheduler modes and sticky/fresh-account rechecks. Group membership, availability, model mapping, capability, channel and profit gates still apply.
- AC3: Cross-platform requests and published model candidates must match the group model family after account mapping; unknown/other-family mappings fail closed. Same-platform behavior stays compatible.
- AC4: Messages, Chat Completions and Responses entry points use the selected account's existing compatible forwarding profile, including streaming; forwarding never changes account platform or group billing/quota identity. Google-native `/v1beta` keeps native Gemini/opt-in Antigravity accounts; this change adds no new wire protocol.
- AC5: Model lists/metadata and UI candidates agree with scheduling. Cross-group accounts remain excluded. Cline pass/credit cooldowns remain tied to the mapped upstream model.

## Implementation and verification

Binding compatibility is centralized in domain/platforms.go and frontend/constants/platforms.ts. Provider groups accept their native accounts plus OpenCode, Command Code and Cline. Composite and Antigravity opt-in behavior remains independent. Account.SupportsGroupPlatformModel resolves the account mapping before checking the model family; ordinary model/capability/channel/profit/availability gates still run. An unmapped conventional model ID can be used when its family is known and the account supports it; an unknown alias fails closed.

Scheduler pools union the existing exact-platform buckets, retaining group membership and native cache invalidation. Up to three additional cached bucket reads are made per provider-group selection. There are only three supported multi-model providers; investigate batching if measured scheduler p95 materially rises or this set expands. The gateway owner owns that optimization. No snapshot schema or bucket identity changes.

Messages/Chat/Responses provider handlers reuse the OpenAI gateway for the selected multi-model account. The complete OpenAI result is retained for its native usage recorder, preserving cache/image/search fields and pricing candidates; the small ForwardResult projection serves the handler lifecycle. Quota and rate attribution still uses the original group. The upstream profile remains authoritative: for example, OpenCode's existing Gemini/Jev restrictions are not removed by group binding.

Reference coverage also includes upstream `gateway_service.go`, `gateway_forward_as_{chat_completions,responses}.go`, `gemini_messages_compat_service.go`, `openai_{models_list,codex_models_service,codex_model_metadata}.go`, handler dispatchers and their tests. These are compared against the fixed reference above; fork-only modularized paths retain their existing contracts.
