# 支付会话弹层设计 — 2026-09-13

支付页面统一采用一份 Payment Session 状态：`creating` → `awaiting_payment` → `paid_processing` → `completed`，并保留 `cancelled`、`expired`、`failed`、`manual_review`。支付宝、微信、未来 TTS 的重置卡都只提供不同的 launch mode（真实 QR、托管跳转、深链、JSAPI），共用金额、倒计时、轮询、取消、关闭和恢复。

桌面端使用居中的 `PaymentSessionModal`，移动端使用带安全区的 bottom sheet。关闭只隐藏面板并保留订单恢复上下文；取消是独立的、明确的订单操作。浏览器固定回跳页仍作为兼容桥，不能把 URL 参数当作支付或履约凭据。

统一支付服务目前只对微信返回 Native `checkout_code_url`，支付宝返回托管收银台 URL。支付宝不能把托管 HTML/签名 URL 当 QR 内容。若后续商户开通 `alipay.trade.precreate`，新增请求级 `native_qr` 展示能力，后端返回真实 `qr_code`；precreate 歧义时进入确认中并查单，不自动创建第二笔交易。未来 TTS 重置卡复用 `order_type=reset_card` 和同一会话状态，服务端按目标订阅快照履约。

## 重置卡外部支付的发布与回滚边界

`reset_card` 已从站内余额扣款改为真实支付宝/微信订单。发布前必须先只读确认 `subscription_reset_grants.payment_order_id` 没有重复的非空值，再执行 migration 244；若发现重复，停止迁移并人工核对订单、发卡记录和审计证据，不能删除记录来强行通过唯一索引。

所有会接收支付回调、公开查单或运行履约恢复任务的节点必须同时升级到识别 `reset_card` 且未知订单类型 fail closed 的版本，之后才能允许新的重置卡外部下单。任何仍可能处理重置卡订单的旧版本会把未知类型落入余额履约，因此不能混合运行。

支付实例一旦产生订单，其商户身份、验签密钥和渠道凭据不得原地覆盖或删除。轮换时新建实例，再停用旧实例；旧实例保留用于历史订单的回调验签、查单和退款。微信回调在解密前无法取得商户订单号，因此已停用但确有历史订单的微信实例仍作为验签候选；本地实例或凭据暂时不可用时回调必须返回可重试错误，不能用成功响应丢弃通知。

新订单会在不保存密钥的 provider snapshot 中固定实例、商户身份、支付模式和币种；微信还固定实际使用的 `jsapi`、`h5` 或 `native` checkout mode。重试先按确定的商户订单号查单，只有渠道明确返回不存在后才允许按完全相同的模式重建；缺少 checkout mode 的旧微信快照可以查单，但不能猜测模式后重建。所有渠道在建单事务内锁定并重读实例配置，运行时配置无法读取或解密时失败关闭。

重置卡订单的本地有效期至少覆盖渠道五分钟最短支付窗口、两分钟创建租约和一分钟安全余量。真正调用渠道前再次读取 `payment_enabled` 并按剩余秒数写入支付宝/微信的渠道过期时间；剩余时间不足时保留待查单标记，不再新建渠道交易。支付成功后的发卡仍以结算时锁定的订阅状态和快照截止时间为准，超过承诺有效期的订单进入人工处理，不能无限自动重试。

只要库中仍有可回调或可恢复的重置卡订单，就不能直接回滚到旧 binary。当前没有独立的重置卡支付开关，回滚时先将 `payment_enabled=false`（入口继续保持关闭），由新版本继续接收回调和运行恢复，核对并处理所有 `PENDING`、已付款 `PAID/RECHARGING/FAILED` 及需要人工处理的订单；确认旧版本不会再接触这些订单后才能切换。订单、发卡记录、审计日志和 provider snapshot 全部保留。
