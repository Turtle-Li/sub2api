## 分析与变更记录

### 分析结论与修复责任

- 支付导航（F01）：`ShopProductView` 将弹窗关闭、取消、成功都接到同一个进入订单详情的函数；取消提交后共享组件会先发 `settled(cancelled)` 再发 `done`。改为记录终态，只在用户确认成功提示后进入订单；取消留在商品购买页，下一次明确购买才生成新幂等键，关闭待付款窗口继续使用原键。责任：主任务。
- 小窗口（F02）：共享支付组件已有 iframe `load` 后隐藏返回页的处理，但子页面仍先渲染完整订单/导航，并可能读取另一次付款的本地恢复记录。改为嵌入返回页只呈现紧凑确认状态、向自身父窗口发送就绪提示，由父窗口查询自己的订单；同源、准确窗口来源是消息边界，消息和 URL 参数均不能作为支付凭证。命名付款弹窗也使用紧凑状态，保留原有服务端查单。仅补商城付款的恢复快照，不改注册 ReturnURL、签名、退款或回调协议。责任：主任务。
- 充值资料与交付界面（F03–F07、F09–F11、F14）：深色说明块缺内边距、输入框禁止折行，第一次提交在检查成功后直接返回；复制反馈写入顶部消息，列表只看订单类型，不看真实履约资格。修复视觉间距、一次提交链和异步归属；交付资格由后端投影并由列表保守消费；复制与并发字段保持安全边界。责任：独立 UI 工作树，资格投影由后端工作树负责。
- 通知（F08、F12、F13）：商城通知标题未区分业务；自动履约异常候选和历史重检未排除人工交付单；提醒仅按入队时间限频，延迟送达后可能很快再次发送。修复业务标题，静默关闭误报并抑制历史待发任务，按实际送达时间维持至少 20 分钟间隔；保留真实自动履约与退款复核告警。责任：独立后端工作树。
- 邮件（F15）：生产订单 65 的完成邮件 outbox 为 `SENT`、一次尝试，`sent_at=2026-11-05T02:51:41.209102+08:00`。当前付款/履约均完成，排除过期任务跳过分支；邮件实现仅在 SMTP DATA 完成并被接受后返回成功。这证明 SMTP 已接受，不证明邮箱最终收件或未进垃圾箱。未发现可据以更改 SMTP 配置或重发的失败证据；本次不虚构邮件修复。

上述前端导航、资料提交和通知根因为代码直接证据，置信度高；用户看到小窗口完整页面的具体时序为推断，需用真实浏览器的嵌入返回场景证明新行为。风险集中在重复付款、异步提交旧资料、错误展示支付成功和错误抑制告警，均纳入回归。
