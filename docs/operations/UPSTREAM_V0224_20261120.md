## 后续兼容：Responses WS `ctx_pool` 的 `upstream_unavailable`

CPR 可以在报告本轮失败后保持 WebSocket 开放，等待下一轮，不再发 `response.failed`。
原来客户端已看到错误，但用户和共享账号槽仍等普通读超时。**不缩短 900 秒的正常单次读超时，
也不给裸错误统一设 2 秒截止。** 本地复现了错误先到、2.5 秒后 `response.failed` 才带真实
usage 的情况：旧草案在第 2 秒已用空结果结算。

- 先走已有上下文恢复和明确限流/容量处理。只在已配置的 CPR 额度同步账号上，把 CPR 自己生成的
  502/503 `error`（`server_error` / `upstream_unavailable`）认作本轮终态：必须有非空且一致的
  `request_id` 和 `headers.x-gateway-request-id`、有效的 `x-request-id` 或 `x-oai-request-id`，
  且顶层及 `error` 对象均无额外字段（例如 `response`/`usage`）。不得仅凭错误码、消息文案或账号名称判定。
- 原样交付该失败，按原下行写超时处理客户端背压。写入或断开后直接释放本轮用户和共享账号两个槽，丢弃上游连接，不重放、不绑定失败的续链。
  未报告用量不造账；已报告的 token 或已完成的图片由原计费链结算一次，仍是失败请求。
- 未确认来源/形状的同码错误照常等待权威终态或原读超时，真实用量优先。若对方只发模糊
  错误而不结束，这类连接仍可能占槽；不能把 CPR 的契约推广给其他中转。正常长轮次、HTTP/SSE
  和 WS passthrough 均不改变，也不靠自动重发来恢复结果不明的请求。
