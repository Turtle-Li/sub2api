## Integration seams and contracts

- Payment and site mode: adopt the upstream EasyPay rule that permits periods
  in an upstream method code. Keep the custom method's public code restricted
  to the existing safe alphabet. Compose upstream `subscription_enabled` and
  `payment_balance_disabled` with the fork's independent
  `payment_entry_enabled`; the public settings payload must expose all three
  decisions as well as the fork's settlement-currency projection. A site-mode
  edit does not implicitly open customer checkout. New subscription orders are
  also rejected at the payment service boundary whenever
  `subscription_enabled=false`. The handler first restores the signed WeChat
  resume claims, so changing an OAuth return URL from `subscription` to
  `balance` cannot bypass that rule. The production purchase entry remains
  closed until the owner tests the released flow. The 2026-09-15
  read-only preflight found `payment_enabled=true`,
  `payment_entry_enabled=false`, `BALANCE_PAYMENT_DISABLED=false`, and no
  stored subscription-disabled key; the resulting mode is recharge plus
  subscription with customer purchase discovery still closed.
- Upstream payment overlap: the upstream-only payment changes in this release
  are the EasyPay upstream-code alphabet, the three-state site billing mode,
  serialized subscription extensions, bounded subscription bulk actions, and
  a scrollable renewal-plan dialog. The merge uses those upstream paths rather
  than parallel fork implementations. Upstream has no equivalent for audited
  historical grant backfill, reserved proportional refunds, separate refund
  entitlement state, reset-card tier provenance, or idempotent monthly card
  delivery, so those remain fork-owned extensions around the upstream
  subscription transaction boundary.
- Unified payment: retain the fork's `pay-v1`/Ed25519 gateway, Vault-backed
  identity, signed webhook inbox, asynchronous and partial refund adapter,
  provider-source routing, and local order/fulfilment authority. These are an
  intentional replacement for direct provider custody and are not superseded
  by the upstream payment changes. The final merge keeps the local parent's
  `backend/internal/payment/unifiedpay`, unified binding
  handlers/repository, unified migrations, and gateway wiring unchanged. Wire
  still constructs `ProvideUnifiedPaymentGateway`,
  passes it to `ProvidePaymentService`, starts refund reconciliation, and
  exposes `/api/v1/payment/webhook/unified` plus the administrator binding
  routes. The only payment-config change from the local parent is the
  server-side projection of `subscription_enabled` used for this authorization
  check; it does not change provider selection or settlement. Focused
  unified-payment and refund-webhook tests pass after the merge.
- Subscription management: adopt serialized extension and bounded bulk
  actions, while preserving both fork reset-card grant endpoints. The existing
  database refund-hold guard remains authoritative: an extension, shortening,
  revoke, or other term mutation that conflicts with a reserved paid refund
  must fail instead of changing the entitlement underneath the refund worker.
  The historical order backfill also continues to reject a second refund
  reservation on the same subscription.
- OpenCode: adopt the Zen/GO account and routing support. Migration
  `238_opencode_go_platform.sql` only widens platform constraints and keeps the
  previously deployed MiniMax value. The migration runner identifies files by
  full filename and checksum, so it can coexist with the fork's
  `238_feishu_payment_incidents.sql` and the upstream
  `238_purge_unlimited_user_platform_quotas.sql`. Rehearsal applied the OpenCode
  migration twice and retained both MiniMax and OpenCode in all four platform
  constraints; PostgreSQL reported no invalid indexes and `pg_amcheck` passed.
- Quota cleanup: the upstream purge removes only `user_platform_quotas` rows
  whose daily, weekly, and monthly limits are all NULL. Such rows are already
  read as unlimited; rows with any configured limit, including zero, remain.
  The 2026-09-15 read-only production preflight found 145 rows, all 145 with
  the three limits NULL and zero configured-limit rows. Rehearse the exact
  deletion and the post-migration unlimited behavior on a production backup.
  The restored production backup rehearsal deleted exactly those 145 rows on
  the first run and zero on the second; user, subscription, payment-order, and
  subscription-grant signatures remained unchanged.
- Images and OpenAI WebSocket: retain the fork's fixed account-admission,
  exactly-N multi-image, request replay, settlement accounting, and deployment
  behavior while adopting the upstream direct Images path, namespace fixes,
  raw-input memory reduction, execution-scope isolation, queue reselection,
  ping handling, and connection-capacity corrections. Combined tests must
  cover both sets of behavior. The upstream native Images route is also marked
  as a gateway-built request before transport selection, matching the existing
  Responses fallback. This preserves the fork's image-scope capability-loss
  cooldown without applying it to client-controlled passthrough requests.
- Proxy credentials: use upstream pointer presence semantics so an omitted
  username/password is preserved and an explicit empty value clears it. Apply
  the result to the fork's copied update candidate before the fixed-egress
  identity check, so protected OAuth proxy identity still cannot drift and the
  one-way legacy credential cleanup remains possible.
- Deployment: Apple-container self-update changes do not replace this fork's
  canonical GitHub Actions blue-green receiver, maintenance lock, readiness
  probe, Caddy verification, or guarded rollback path. The upstream compact
  model default changes to GPT-5.5. The 2026-09-15 production preflight found
  no `GATEWAY_OPENAI_COMPACT_MODEL` override, so this is an effective runtime
  change and must remain in the combined gateway regression scope.
