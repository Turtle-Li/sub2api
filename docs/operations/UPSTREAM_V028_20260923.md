## OpenCode Go usage windows (add/add)

Both sides shipped this feature. The fork cherry-picked the upstream work in
progress (`78a33c62a`, `ca4688d31`) and then added fork-only fixes: relay and
`upstream`-type account support, proxy-scoped snapshot isolation, URL-keyword
classification, and canonical base-URL rewriting. Upstream continued on its own
line with `d03274ad5` (eligibility generalised to the `opencode_go` platform and
a mount whitelist) and `a2e161870` (CASE evaluation order and mode guards).

The merged eligibility rule is the union, and it is mirrored on both sides of
the process boundary:

- `service.IsOpenCodeGoUsageAccount` requires `type ∈ {apikey, upstream}` (fork:
  imported relay/upstream accounts carry the same `base_url` + `api_key` shape).
- `platform == opencode_go` is authoritative and defers to `IsOpenCodeGoPlan`
  (upstream): Go subscription yes, Zen pay-as-you-go no, `base_url` irrelevant.
- Other platforms must be in `isOpenCodeGoUsageMountPlatform`
  (`openai/anthropic/kimi/zhipu/deepseek/minimax`, upstream) and then go through
  the fork's saved-URL rule: exact official base accepted, any other URL on the
  official host rejected, otherwise the `opencode` / `deepseek` keyword
  precedence decides. The keyword branch is what keeps the fork's live
  third-party relay accounts eligible; upstream's URL-only predicate would drop
  them.

`repository.opencodeGoUsageEligibleSQLFor` is the SQL mirror of that rule:
upstream's `opencode_go` + `account_mode <> 'zen'` branch, the shared
`opencodeGoUsageMountPlatformsSQL` whitelist, the fork's
`opencodeGoUsageURLMatchSQL` keyword predicate, and the fork's
`type IN ('apikey','upstream')`. The same three-part predicate is used by the
`lockAndMergeAccountProbeExtra` identity-unchanged check, the `UpdateCredentials`
CASE branch, and the `BulkUpdate` identity-cleanup clauses. The OpenCode CASE
branch must stay ahead of the Ollama branch: the two `WHEN` clauses are not
mutually exclusive once the platform whitelists are identical, and reordering
would let an `api_key` change hit the Ollama branch and carry a stale OpenCode
snapshot onto the new key.

Fork behaviour kept on top of upstream's version of the service:
`openCodeGoUsageSnapshotSourceKey` (a snapshot from a different proxy never
refills a row whose own snapshot was invalidated, while the auto-refresh switch
stays group-wide), the three-value `tryAcquireSingletonLeaderLock` lease, and
`canonicalOpenCodeGoUsageBaseURL`, which `buildAnthropicMessagesEndpointURL` and
`Account.GetOpenAIBaseURL` still depend on.

Frontend: the fork's `OpenCodeGoUsageCell.vue` is kept (inline refresh error,
eager refresh on mount, URL-derived eligibility) with its platform list widened
to the same mount whitelist plus the `opencode_go` platform branch. Upstream's
duplicate cell placement inside the generic key-account block was dropped; the
fork's today-stats-first placement is the tested layout. `proxy_repo`'s snapshot
invalidation adopts upstream's broadened platform predicate.

## Reasoning-effort billing migration

Upstream migration `239_channel_reasoning_effort_multipliers.sql` replaces the
scalar `max_reasoning_effort_multiplier` with a
`reasoning_effort_multipliers` JSONB map on `channel_model_pricing` and
`channel_account_stats_model_pricing`, and rewrites the equivalent key inside
`groups.model_pricing`. The fork's `currency` column (migration 242) is an
independent column on the same tables, so the two coexist; every conflicted
SELECT/INSERT/UPDATE in `channel_repo_pricing.go` and
`channel_repo_account_stats_pricing.go` now carries both `currency` and
`reasoning_effort_multipliers`, and `ChannelModelPricing` keeps `Currency`
while `MaxReasoningEffortMultiplier` is gone.

Replay properties verified against a real PostgreSQL instance by
`TestMigration239ReasoningEffortMultipliers` (integration tag, testcontainers):
the column add is guarded by an `attisdropped`-aware existence check so a replay
does not revive a deliberately cleared map, and the `groups.model_pricing`
rewrite is idempotent because it removes the consumed legacy key. Migrations are
tracked per filename with a checksum, so inserting `238b`/`239`/`240` into a
database that already applied the fork's `241`–`257` simply applies the three
new files; filename ordering never re-runs an applied migration.

`ReasoningEffortMultipliers` is deliberately not gated by
`allowChannelMultipliers`, matching upstream — account-statistics pricing also
carries the column.

  `scanContentModerationLog` helper is extended with `engine_meta` and both the

  restoration supersede upstream's `Set`-based scroll lock, which was removed.
- `release.yml`: keep the fork's manual-dispatch-only trigger and its rationale
  comment, add upstream's repository-scoped `concurrency` group. The duplicate
  `env` block upstream added lower in the file is the surviving one.
- `.gitignore` and the Compose files keep both sides' additions (fork doc

- `docs/ANTIGRAVITY_ATTRIBUTION_429.md` was removed upstream as PR noise but is
